Chapter 01Beginner → Advanced

Python — Complete

Python is the engine of your entire backend. You must know it deeply — not just syntax, but how Python thinks.

Core language — foundations
Variables & types
Data types & type system
int, float, str, bool, None. Python is dynamically typed — variables don't have fixed types. type(x) checks type at runtime.
Python uses "duck typing" — if it walks like a duck and quacks like a duck, it's a duck. Django's ORM relies on this heavily.
Data structures
Lists, dicts, sets, tuples
List: ordered, mutable. Dict: key-value, ordered (3.7+). Set: unique values. Tuple: immutable. Know when to use each.
Django querysets return dict-like objects. Knowing dict operations cold makes ORM work effortless.
Control flow
if/else, loops, comprehensions
for loops, while loops. List comprehensions: [x*2 for x in items]. Dict comprehensions. Generator expressions.
List comprehensions are 35% faster than equivalent for loops. Use them everywhere in Django views.
Functions
Functions, args, kwargs
*args = positional arguments list. **kwargs = keyword arguments dict. Default parameters. Lambda functions. First-class functions.
Django's CBVs (Class-Based Views) pass everything through **kwargs. If you don't understand this, CBVs will be confusing forever.
OOP
Classes & OOP principles
class, __init__, self, inheritance, super(). Properties. Dunder methods: __str__, __repr__, __len__. Encapsulation.
Every Django model is a Python class. Every Django view can be a class. OOP isn't optional — it's the foundation of Django.
Decorators
Decorators — Django's secret weapon
Functions that wrap other functions. @login_required, @property, @staticmethod. Write your own decorators.
@login_required, @permission_required, @cache_page — all of Django's most powerful features are decorators. Master this pattern first.
Intermediate Python
Modules
Modules, packages, imports
import, from x import y, relative imports. __init__.py. Understanding how Python finds modules.
Django's entire app system is just Python's import system. If you understand how imports work, Django's apps.py and AppConfig make immediate sense.
Error handling
Exceptions & error handling
try/except/finally. Raising exceptions. Custom exception classes. Exception hierarchy. Logging errors properly.
Never catch bare except: — it hides bugs. Always catch specific exceptions. In Django APIs, exceptions become HTTP error responses.
Files & IO
File handling & context managers
with open() as context manager. Reading/writing text and binary files. pathlib for modern file paths. os module.
Django's file upload system uses Python file objects. Understanding context managers (with statement) prevents memory leaks.
Iterators
Iterators & generators
yield keyword. Generator functions. __iter__ and __next__. Lazy evaluation saves memory on large datasets.
Django QuerySets are lazy iterators — they don't hit the database until you iterate them. This is why you see list(queryset) to force evaluation.
Environments
Virtual environments & pip
python -m venv venv. Activating. pip install. requirements.txt. Never install packages globally.
Every Django project MUST have its own venv. Package conflicts will ruin your career if you skip this. Use pip freeze > requirements.txt always.
Advanced
Type hints (Python 3.9+)
def greet(name: str) -> str:. List[int], Dict[str, Any], Optional[str]. mypy for type checking.
DRF serializers benefit enormously from type hints. They catch bugs before runtime and make API code self-documenting.

Chapter 02Beginner → Intermediate

MySQL & Databases

Every piece of data in your app lives in MySQL. Understanding it deeply makes Django's ORM a superpower instead of a black box.

SQL fundamentals
DDL
CREATE, ALTER, DROP
CREATE TABLE defines structure. ALTER TABLE modifies it. DROP TABLE removes it. Django migrations do all of this automatically.
Django migrations are just Python code that generates these SQL statements. Reading migration files teaches you what Django is actually doing to your database.
DML
SELECT, INSERT, UPDATE, DELETE
The 4 basic operations. WHERE filters. ORDER BY sorts. LIMIT paginates. GROUP BY aggregates. These map directly to Django ORM methods.
Django ORM's .filter() = WHERE, .order_by() = ORDER BY, .values() = SELECT specific columns. Know SQL first, ORM later.
Joins
INNER, LEFT, RIGHT JOIN
INNER JOIN: matching rows only. LEFT JOIN: all left rows + matching right. RIGHT JOIN: opposite. Combines data from multiple tables.
Django's select_related() generates SQL JOINs. Without knowing joins, you'll never optimize N+1 query problems — the #1 performance killer.
Indexes
Indexes & query performance
Indexes speed up lookups dramatically. Primary key always indexed. Add indexes to columns you filter/sort by frequently. EXPLAIN ANALYZE shows query plans.
A missing index on a foreign key column can make a page load 100x slower. Django's db_index=True on model fields adds them automatically.
Normalization
1NF, 2NF, 3NF explained
1NF: atomic values, no repeating groups. 2NF: no partial dependency. 3NF: no transitive dependency. Good design prevents duplication and inconsistency.
Most Django models follow 3NF naturally if you use ForeignKey correctly. Denormalization (breaking rules intentionally) is a valid optimization for read-heavy APIs.
Transactions
ACID & transactions
Atomicity, Consistency, Isolation, Durability. BEGIN/COMMIT/ROLLBACK. All-or-nothing operations. Critical for financial/inventory data.
Django's transaction.atomic() wraps operations in a transaction. If any step raises an exception, the entire operation is rolled back. Use it for any multi-step save operation.
Essential SQL you must know cold
essential_queries.sql
-- Basic SELECT with filter and sort
SELECT id, username, email
FROM users
WHERE is_active = 1 AND role = 'admin'
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;

-- JOIN (used by Django select_related)
SELECT orders.id, users.username, orders.total
FROM orders
INNER JOIN users ON orders.user_id = users.id
WHERE orders.status = 'pending';

-- Aggregation (used by Django annotate/aggregate)
SELECT category, COUNT(*) as count, AVG(price) as avg_price
FROM products
GROUP BY category
HAVING COUNT(*) > 5;

-- Subquery
SELECT * FROM users
WHERE id IN (
    SELECT user_id FROM orders
    WHERE total > 1000
);

-- Index creation (Django: db_index=True)
CREATE INDEX idx_users_email ON users(email);
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'x@x.com';
🔑The N+1 query problem — the most common performance bug in Django. It happens when you loop over a queryset and access a related object inside the loop, firing one extra DB query per row. Fix: queryset.select_related('author') or queryset.prefetch_related('tags'). Always check Django Debug Toolbar to spot this.

The Django ORM — complete guide
Models
Defining models
Each model = a DB table. Fields define columns. Meta class adds options. __str__ defines string representation.
Always define __str__ on every model. Django admin, shell, and DRF all use it to display objects. Skip it and debugging becomes painful.
Relationships
ForeignKey, ManyToMany, OneToOne
ForeignKey = one-to-many. ManyToManyField = many-to-many (creates junction table). OneToOneField = one-to-one. on_delete behavior matters.
related_name is the most missed concept. ForeignKey(User, related_name='posts') lets you do user.posts.all() — essential for API design.
Querying
QuerySet API
.all(), .filter(), .exclude(), .get(), .create(), .update(), .delete(), .order_by(), .values()
QuerySets are lazy. qs = Post.objects.filter(active=True) doesn't hit DB. Only iteration, len(), list(), or template rendering triggers the query.
Lookups
Field lookups & Q objects
__exact, __contains, __icontains, __gt, __lt, __in, __startswith. Q objects for complex OR/AND queries.
Q(name__icontains='ali') | Q(email__icontains='ali') — this is how you build search functionality. Combine multiple Q objects for complex searches.
Migrations
makemigrations & migrate
python manage.py makemigrations creates migration files. migrate applies them to the database. Never edit migration files manually.
Always commit migration files to git. If your team has migration conflicts, use python manage.py squashmigrations to clean up. Never delete migrations from a production app.
Optimization
select_related & prefetch_related
select_related: follow ForeignKey via SQL JOIN. prefetch_related: separate query for ManyToMany/reverse FK. Eliminates N+1.
Profile your queries with Django Debug Toolbar. A list page showing 20 posts with author names can fire 21 queries without select_related. With it: just 1.
Django project structure & setup
models.py — complete model example
from django.db import models
from django.contrib.auth.models import User

class Category(models.Model):
    name = models.CharField(max_length=100, unique=True)
    slug = models.SlugField(unique=True)

    class Meta:
        verbose_name_plural = 'categories'
        ordering = ['name']

    def __str__(self):
        return self.name

class Post(models.Model):
    STATUS = [('draft', 'Draft'), ('published', 'Published')]

    title     = models.CharField(max_length=200)
    body      = models.TextField()
    author    = models.ForeignKey(User, on_delete=models.CASCADE,
                                   related_name='posts')
    category  = models.ForeignKey(Category, on_delete=models.SET_NULL,
                                   null=True, related_name='posts')
    tags      = models.ManyToManyField('Tag', blank=True)
    status    = models.CharField(max_length=10, choices=STATUS,
                                  default='draft')
    created   = models.DateTimeField(auto_now_add=True)
    updated   = models.DateTimeField(auto_now=True)

    class Meta:
        ordering = ['-created']
        indexes = [models.Index(fields=['status', '-created'])]

    def __str__(self):
        return self.title

# ORM queries
posts = Post.objects.filter(status='published').\
    select_related('author', 'category').\
    prefetch_related('tags')
Django authentication system
Auth
Built-in User model
Django ships with a complete user system: login, logout, password hashing, sessions, permissions. Use it — don't build your own.
Always use a custom user model from the start: class User(AbstractUser) in a separate app. Changing the user model later is extremely painful.
Permissions
Permissions & groups
Every model gets 4 permissions: add, change, delete, view. Group users for role-based access. @permission_required decorator.
Use user.has_perm('app.action_model') in views and templates. Design your permission system before you build the API — retrofitting it is hard.

Complete DRF example — Posts API
api/serializers.py
from rest_framework import serializers
from .models import Post, Category

class CategorySerializer(serializers.ModelSerializer):
    class Meta:
        model = Category
        fields = ['id', 'name', 'slug']

class PostSerializer(serializers.ModelSerializer):
    # Nested serializer — category becomes an object not just an id
    category = CategorySerializer(read_only=True)
    category_id = serializers.PrimaryKeyRelatedField(
        queryset=Category.objects.all(), source='category', write_only=True
    )
    author_name = serializers.SerializerMethodField()

    def get_author_name(self, obj):
        return obj.author.get_full_name() or obj.author.username

    def validate_title(self, value):
        # Custom field validation
        if Post.objects.filter(title=value).exists():
            raise serializers.ValidationError("Title already exists.")
        return value

    class Meta:
        model = Post
        fields = ['id','title','body','category','category_id',
                  'author_name','status','created']
        read_only_fields = ['id', 'created', 'author_name']
api/views.py
from rest_framework import viewsets, permissions, filters
from rest_framework.decorators import action
from rest_framework.response import Response
from django_filters.rest_framework import DjangoFilterBackend

class PostViewSet(viewsets.ModelViewSet):
    serializer_class = PostSerializer
    permission_classes = [permissions.IsAuthenticatedOrReadOnly]
    filter_backends = [DjangoFilterBackend, filters.SearchFilter,
                       filters.OrderingFilter]
    filterset_fields = ['status', 'category']
    search_fields = ['title', 'body']
    ordering_fields = ['created', 'title']

    def get_queryset(self):
        # Only show own posts for non-staff users
        if self.request.user.is_staff:
            return Post.objects.all().select_related('author', 'category')
        return Post.objects.filter(author=self.request.user)

    def perform_create(self, serializer):
        # Auto-set author to current user
        serializer.save(author=self.request.user)

    @action(detail=True, methods=['post'])
    def publish(self, request, pk=None):
        # Custom action: POST /api/posts/1/publish/
        post = self.get_object()
        post.status = 'published'
        post.save()
        return Response({'status': 'published'})

AJAX — Deep Dive

AJAX is how your frontend talks to your Django API. This chapter focuses on AJAX specifically in the context of DRF — the patterns you'll use every day at work.

The fetch() API — complete professional patterns
api.js — reusable AJAX client
// api.js — a production-ready AJAX client for your DRF backend
const API_BASE = 'http://localhost:8000/api';

function getToken() {
    return localStorage.getItem('access_token');
}

async function apiFetch(endpoint, options = {}) {
    const url = `${API_BASE}${endpoint}`;
    const token = getToken();

    const config = {
        headers: {
            'Content-Type': 'application/json',
            ...(token ? { 'Authorization': `Bearer ${token}` } : {}),
            ...options.headers
        },
        ...options
    };

    const res = await fetch(url, config);

    // Auto-refresh token on 401
    if (res.status === 401) {
        const refreshed = await refreshToken();
        if (refreshed) return apiFetch(endpoint, options);
        window.location = '/login';
    }

    if (!res.ok) {
        const err = await res.json().catch(() => ({}));
        throw { status: res.status, data: err };
    }

    if (res.status === 204) return null; // No content (DELETE)
    return res.json();
}

// Clean API methods
const api = {
    get:    (url)         => apiFetch(url),
    post:   (url, data)   => apiFetch(url, { method: 'POST',   body: JSON.stringify(data) }),
    put:    (url, data)   => apiFetch(url, { method: 'PUT',    body: JSON.stringify(data) }),
    patch:  (url, data)   => apiFetch(url, { method: 'PATCH',  body: JSON.stringify(data) }),
    delete: (url)         => apiFetch(url, { method: 'DELETE' }),
};

// Usage
const posts = await api.get('/posts/?status=published');
const post  = await api.post('/posts/', { title: 'Hello', body: '...' });
await         api.delete(`/posts/${id}/`);

// Django requires CSRF token for non-GET requests from browser clients
// For DRF with JWT: disable CSRF (JWT is already stateless)
// For Django sessions: always include the CSRF token

function getCsrfToken() {
    return document.cookie
        .split(';')
        .find(c => c.trim().startsWith('csrftoken='))
        ?.split('=')[1];

// Include in AJAX headers when using session auth

AJAX patterns every developer must know
Pattern
Optimistic UI updates
Update the UI immediately before the API responds. If the API fails, roll back. Feels instant to the user.
Twitter/X uses this for likes. Your heart turns red instantly — the API is still running. If it fails, it turns grey again. Implement this for any toggle/like action.
Pattern
AbortController
Cancel in-flight requests when a new one supersedes them. Essential for search boxes, autocomplete, and filters.
Without this, typing "react" fires 5 requests. If the "r" request responds last, you show wrong results. AbortController prevents this race condition.
Pattern
Debouncing search
Wait 300ms after the user stops typing before firing the request. Reduces API calls from 10 to 1 per search.
Combine debounce + AbortController for bulletproof search. Debounce reduces calls. AbortController handles the ones that slip through.
Pattern
Pagination with AJAX
DRF returns {"count":100,"next":"?page=2","results":[]}. Load more button or infinite scroll. Never load all data at once.
DRF's PageNumberPagination gives you next and previous URLs. Store the next URL and hit it when user scrolls to bottom.

React — Complete Guide

React is your frontend engine. You'll use it to build every UI that talks to your Django API.

React mental model
🔑React's core idea: UI = f(state). Your interface is just a function of your data. When state changes, React re-renders the component. That's it. Everything else (hooks, context, useEffect) is building on this idea.
The hooks you must master
Hook
useState
const [value, setValue] = useState(initial). Triggers re-render when set. The foundation of all interactivity.
Never mutate state directly (state.push()). Always create a new value: setItems([...items, newItem]). Mutation doesn't trigger re-renders.
Hook
useEffect
Run side effects: fetch data, subscriptions, timers. Dependency array controls when it runs. Return a cleanup function.
useEffect with [] runs once on mount (= fetch data on load). With [id] runs when id changes (= fetch new data when route changes). Missing deps = stale closures.
Hook
useContext
Share state across components without prop drilling. Create a context, provide it at the top, consume it anywhere below.
Use context for: auth state (current user), theme, language. Don't use it for everything — it causes all consumers to re-render when the value changes.
Hook
useReducer
Like useState but for complex state logic. dispatch({ type: 'INCREMENT' }) — a reducer function handles transitions.
Use useReducer when you have 3+ related state values that change together, or when the next state depends on the previous. Forms with many fields are a perfect use case.
Hook
useMemo & useCallback
Memoize expensive calculations (useMemo) or function references (useCallback). Prevents unnecessary re-computation.
Don't reach for these first. Profile with React DevTools Profiler. If a component re-renders 60+ times per second, then memoize. Premature optimization wastes time.
Hook
Custom hooks
Extract reusable stateful logic into functions starting with use. useApi, useAuth, useLocalStorage.
Every time you copy-paste a useEffect+useState combo for fetching data, you should create a custom hook instead. This is how you build a maintainable codebase.
Custom hook — useApi (fetch data from DRF)
hooks/useApi.js
import { useState, useEffect, useCallback } from 'react';

export function useApi(url, options = {}) {
    const [data,    setData]    = useState(null);
    const [loading, setLoading] = useState(true);
    const [error,   setError]   = useState(null);

    const fetchData = useCallback(async () => {
        setLoading(true);
        setError(null);
        try {
            const res = await fetch(url, {
                headers: {
                    'Authorization': `Bearer ${localStorage.getItem('token')}`
                }
            });
            if (!res.ok) throw new Error(`HTTP ${res.status}`);
            const json = await res.json();
            setData(json);
        } catch (e) {
            setError(e.message);
        } finally {
            setLoading(false);
        }
    }, [url]);

    useEffect(() => { fetchData(); }, [fetchData]);

    return { data, loading, error, refetch: fetchData };
}

// Usage in any component:
function PostList() {
    const { data: posts, loading, error } = useApi('/api/posts/');

    if (loading) return <Spinner />;
    if (error)   return <Error message={error} />;
    return <PostGrid posts={posts.results} />;
}

}

// React component for file upload to DRF
async function uploadFile(file) {
    const formData = new FormData();
    formData.append('file', file);
    formData.append('title', file.name);

    // NOTE: do NOT set Content-Type manually for FormData!
    // Browser sets it automatically with the correct boundary
    const res = await fetch('/api/uploads/', {
        method: 'POST',
        headers: {
            'Authorization': `Bearer ${token}`
            // No Content-Type here — crucial!
        },
        body: formData
    });
    return res.json();
}
⚠️Common mistake: Setting Content-Type: application/json when sending FormData breaks file uploads. The browser must set Content-Type automatically so it can include the multipart boundary string. Remove the Content-Type header entirely for file uploads.

The secrets that make you a senior developer
⚡
Use Django Debug Toolbar always
Install it in development. It shows every SQL query, how long each took, how many were duplicates. You'll find N+1 problems in minutes that would take hours to diagnose otherwise.
🛡️
Never trust the client
Validate everything on the server. Price, totals, permissions — never compute these on the frontend and send the result. The API must re-validate every piece of business logic.
📦
Use environment variables always
Secret key, database passwords, API keys — never hardcode them. Use python-dotenv + .env files. Add .env to .gitignore on day one. One leaked secret key can end a company.
🔍
Read the source code
Django and DRF are open source. When something is confusing, read the actual source on GitHub. You'll understand it 10x better than any tutorial. This habit separates good from great developers.
🧪
Write tests from the start
Django's test client + DRF's APIClient make API testing trivial. A test suite catches regressions automatically. Companies that don't test deploy broken code to production regularly.
🎯
Learn to read error messages
Read the FULL traceback, bottom to top. The last few lines are usually where the actual error is. Google the exact error message + "Django" or "React". 90% of problems are already solved on Stack Overflow.
🚀
Deploy early, deploy often
Deploy your first project within the first 2 months. The skills to deploy (Nginx, Gunicorn, environment config) are different from development skills. Learn them early.
📚
The official docs are the best docs
Django's documentation is famously excellent. DRF's docs are thorough. React's beta docs are superb. Read them cover-to-cover once. You'll discover features no tutorial ever mentioned.
💬
API design before API code
Design your API endpoints on paper first. What URLs? What HTTP methods? What request/response shapes? Changing an API after the frontend is built is expensive. Design first.
